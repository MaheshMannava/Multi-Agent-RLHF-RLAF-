# Implementation Plan

## 1. Research objective

Reproduce the central contribution of the baseline paper: an interactive Python debugging system that combines specialized syntax and logic agents, reinforcement learning from feedback, and memory-based retrieval.

The first implementation target is a reproducible research prototype, not a production-grade coding assistant.

## 2. System flow

```text
Buggy Python program + tests
            |
            v
  Error classification and observation construction
            |
            v
 Syntax Agent or Logic Agent proposes a structured candidate patch
            |
            v
       Compile program or run tests
            |
            v
 Feedback: accept / reject / correct
            |
            v
     Reward update + episodic memory storage
            |
            v
       Next suggestion or termination
```

## 3. Implementation assumptions

The paper leaves some implementation details unspecified. We will make the following assumptions explicit:

- Agents select from candidate patches generated by repair templates and mutation operators.
- Syntax candidates are generated from compiler diagnostics and nearby source code.
- Logic candidates are generated from common mutation patterns and evaluated with tests.
- Alternating mode is implemented before joint mode.
- Simulated feedback is used before collecting human feedback.
- Program execution is performed in a subprocess with a timeout rather than unrestricted `exec()`.
- The held-out test set is never used for candidate generation, training, or memory construction during training.

## 4. Phased work plan

### Phase 0 — Specification

Deliverables:

- Dataset schema.
- Bug taxonomy.
- Reward definition.
- Evaluation protocol.
- Project structure.

Status: completed in the current planning phase.

### Phase 1 — Dataset and evaluator

Tasks:

1. Create an initial dataset of 20 syntax and 20 logic bugs.
2. Store buggy code, correct code, tests, descriptions, and expected patches.
3. Implement compilation checks for syntax bugs.
4. Implement isolated PyTest execution for logic bugs.
5. Record error messages, failing test IDs, execution time, and success status.
6. Expand to the paper-style 200-program dataset after the evaluator is stable.

Exit criterion: every sample can be evaluated automatically and produces a deterministic success/failure result.

### Phase 2 — Candidate patch generation

Tasks:

1. Implement syntax repair templates.
2. Implement logic mutation operators.
3. Apply each candidate patch to a copy of the program.
4. Remove candidates that do not parse or cannot be executed.
5. Store each candidate with its patch type, line number, modified code, and explanation.

Exit criterion: a candidate list can be produced for every supported bug type.

### Phase 3 — Non-RL baselines

Implement and evaluate:

- Random candidate selection.
- Rule-based candidate selection.
- Supervised candidate ranking.
- Single-agent baseline.
- Multi-agent system without memory.

Exit criterion: baseline scores are available before PPO is introduced.

### Phase 4 — Reinforcement-learning environments

Implement `SyntaxEnvironment` and `LogicEnvironment` using the Gymnasium interface.

Initial observation design:

- Static code and diagnostic features: 30 dimensions.
- Retrieved-memory features: 10 dimensions.
- Natural-language embedding: 768 dimensions.

Initial action design:

- Syntax action: patch type, line, candidate patch, explanation.
- Logic action: candidate patch, failing test ID, explanation.

Exit criterion: environments pass reset/step tests and can be trained with a toy policy.

### Phase 5 — PPO agents and controller

Tasks:

1. Train the Syntax Agent independently.
2. Train the Logic Agent independently.
3. Validate each agent on held-out bugs.
4. Implement alternating mode.
5. Implement joint mode only after alternating mode is stable.

Initial PPO configuration will follow the paper where practical: learning rate `3e-4`, discount factor `0.99`, clip range `0.2`, rollout length `2048`, and batch size `64`.

Exit criterion: PPO results can be reproduced across at least three random seeds.

### Phase 6 — Feedback and memory

Tasks:

1. Add simulated feedback based on ground-truth patches and test outcomes.
2. Add accept/reject/correct reward handling.
3. Store successful debugging episodes.
4. Build CodeBERT and BERT FAISS indices.
5. Retrieve the top five similar records.
6. Compare the full model with no-memory and no-feedback variants.

Exit criterion: memory retrieval and reward updates demonstrably change agent behavior and can be measured by ablation.

### Phase 7 — Human interface and final evaluation

Tasks:

1. Build a minimal feedback interface.
2. Log developer actions in SQLite.
3. Add optional explanations and ratings.
4. Run the final experiments.
5. Prepare tables, plots, limitations, and reproducibility notes.

Exit criterion: the system can support a small pilot study and all reported metrics can be regenerated from saved logs.

## 5. Definition of done

The baseline implementation is complete when it has:

- Separate syntax and logic environments.
- Candidate patch generation.
- PPO agents for both error categories.
- Alternating multi-agent control.
- Simulated feedback and the paper's reward scheme.
- FAISS-based episodic retrieval.
- Held-out evaluation and ablation results.
- A clear record of deviations from the paper.

## 6. Risks and controls

| Risk | Control |
|---|---|
| Logic repair is much harder than syntax repair | Begin with small mutation families and expand gradually |
| PPO receives sparse or noisy rewards | Start with supervised/rule-based baselines and simulated feedback |
| Dataset leakage inflates results | Keep test code and test memory separate from training |
| Arbitrary code execution is unsafe | Use subprocess isolation, timeouts, and restricted working directories |
| Paper details are not reproducible | Document every implementation assumption and deviation |
